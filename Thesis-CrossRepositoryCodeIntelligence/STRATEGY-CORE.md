# استراتژی بی‌زمان: زنجیرهٔ کد ← مشاهده ← شواهد ← گراف ← پرسش ← پاسخِ قابل‌راستی‌آزمایی

> این سند منطق محضِ پروژهٔ Cross-Repository Code Intelligence است — مستقل از تقویم.
> نسخهٔ زمان‌بندی‌شده (هفته‌به‌هفته، شروع از ۱۵ اکتبر ۲۰۲۶) سندی جداست که همین منطق را روی تقویم می‌نشاند.
> هر مرحله در اینجا با یک «تست خروج» بسته می‌شود، نه با یک تاریخ.

جوهر پروژه یک زنجیره است: **کد ← مشاهده ← شواهد ← گراف ← پرسش ← پاسخِ قابل‌راستی‌آزمایی**.
استراتژی از صفر تا صد یعنی این زنجیره را اول به‌صورت یک برش نازکِ کامل بسازی، بعد فقط آن‌قدر پهنش کنی که دادهٔ واقعی توجیه می‌کند، در پایان صادقانه بسنجی، و در طول مسیر پیوسته روایت کنی.

## پنج اصل حاکم

1. **عمق قبل از عرض:** اول یک مسیر کامل سر تا ته (AD-12)، بعد گسترش؛ هیچ دو ماژولِ نصفه به‌طور موازی ساخته نمی‌شود.
2. **داده حکم می‌کند:** هر گسترشی (SQL خام، ADO.NET، Stored Procedure) فقط وقتی ساخته می‌شود که Corpus Census کیس کافی نشان دهد؛ وگرنه Future Work.
3. **صداقت شواهد:** عدم‌قطعیت مقوله‌ای است نه عددی — SUPPORTED / PARTIALLY_SUPPORTED / NOT_ANSWERABLE — و هیچ ارتقای خاموشی به قطعیت رخ نمی‌دهد؛ mapping قراردادی همیشه فلگ ظاهری دارد.
4. **سنجش روی یخ:** داده منجمد، gold منجمد، نتایج خام بدون دست‌کاری — اعتبار علمی پایان‌نامه به همین سه انجماد بسته است.
5. **ردیابی‌پذیری مطلق:** هر خروجی باید به فایل و خط قابل‌بازکردن باشد؛ اگر نبود، هنوز تمام نشده.

## نقشهٔ صفر تا صد

| پرده | پرسش محوری | خروجی کلیدی | تست خروج |
|---|---|---|---|
| ۱. پایه و انجماد | دقیقاً چه می‌سنجیم؟ | manifest + قراردادها + EvidenceRecord | اجرای scan روی دادهٔ منجمد، بدون دست‌کاری |
| ۲. ماشین شواهد | آیا یک مسیر کامل درست کار می‌کند؟ | READ/WRITE صحیح + گراف + کوئری | «چه متدهایی Patients را می‌خوانند؟» با مسیر شواهد کامل |
| ۳. سنجش صادقانه | چقدر خوب؟ کجا شکست می‌خورد؟ | gold + آزمایش‌ها + Antwortbarkeitsmatrix | همهٔ اعداد از اجرای خام بازتولیدپذیر |
| ۴. روایت و دفاع | چرا قابل‌اعتماد است؟ | پایان‌نامهٔ کامل + Kolloquium | reproduction از fresh clone + پاسخ شفاهی به پرسش‌نامه |

هر پرده علاوه بر تست خروج فنی، با یک **checkpoint با استاد** بسته می‌شود (قراردادها، دموی برش عمودی، دموی کوئری‌ها، نتایج، پیش‌نویس). برای پردهٔ ۱ این checkpoint اهمیت دوچندان دارد چون اکسپوزه صراحتاً تأیید Prof. Schmid را روی مرزهای Scope (Ch. 22) پیش‌نیاز می‌داند — پرده تا وقتی که هر دو تست (فنی + تأیید استاد) برقرار نشوند، بسته نمی‌شود.

### پردهٔ ۱ — شناخت و انجماد
1. مفاهیم پایه را خودکار کن: چهار لایهٔ Retrieval-Treffer / Evidence Record / Evidence Path / unterstützter Claim، تمایز پشتیبانی ایستا از رفتار زمان اجرا، تفکیک ساخت کوئری از اجرای آن.
2. Corpus Census را واقعی اجرا کن: تعداد DbContextها، پروژه‌ها، فایل‌های SQL، جایگاه mapping مستقیم در برابر قراردادی — این سند مرز پروژه را تعیین می‌کند.
3. داده را منجمد کن: commit hash + manifest (آدرس، commit، لایسنس، پوشه‌های مستثنا) — کل استدلال reproducibility همین‌جاست.
4. قراردادها را صوری کن: UCها به JSON schema (targetType, allowedScope, requiredRelationTypes, minProvenance, acceptedUncertaintyStates) + کلاس EvidenceRecord با فیلدهای کامل.
5. تصمیم معماری ذخیره‌سازی (in-memory / Neo4j / SQLite) را همین‌جا بگیر و در AD log ثبت کن، چون اسکیمای EvidenceRecord آن را قفل می‌کند.

### پردهٔ ۲ — ماشین شواهد
1. برش عمودی: یک متد واقعی ← کوئری EF ← materialization ← entity ← جدول نگاشت‌شده ← EvidenceRecord با وضعیت SUPPORTED ← تأیید با چشم.
2. دو نوع claim را جدا کن: READ، و WRITE با تفکیک mutation-signal از persistence-trigger؛ mapping قراردادی همیشه با فلگ ظاهری.
3. پهن‌سازی شرطی با حکم census: رشته‌های داینامیک ← UNRESOLVED نه حدس؛ «متد X پروسیجر Y را صدا می‌زند» بدون بدنهٔ پروسیجر هرگز به ادعای سطح جدول ارتقا نمی‌یابد.
4. گراف شواهد: نودها و یال‌ها طبق اسکیما (MAPS_TO, OBSERVES, SUPPORTS, READS_FROM, WRITES_TO, EXECUTES_PROCEDURE) + ایمپورت بدون ID تکراری + تست با fixture مینیمال.
5. لایهٔ پرسش: هر Query Contract به‌صورت traversal + Verifier که پیش از برچسب SUPPORTED هر یال را چک می‌کند.

### پردهٔ ۳ — سنجش صادقانه
1. Goldstandard: راهنمای annotation با نمونه‌های مثبت، منفی، سخت و غیرقابل‌پاسخ ← pilot ← اصلاح قواعد ← فریز test جدا از pilot.
2. اگر annotation مستقل نداری، Kappa گزارش نکن — صداقت روش‌شناسی خودش نقطهٔ قوت دفاع است.
3. آزمایش‌های کنترل‌شده: E0 (متنی) تا E2/E3 (معنایی + mapping)، R0 (متنی) تا R3/R4 (گراف + answerability)؛ هر اجرا predictions / metrics / errors / manifest، بدون هیچ اصلاح دستی.
4. خروجی نقش‌محور: قالب‌های Developer / Architect / QA + تست‌های امتناع (امتناعِ درست با دلیل در برابر امتناع کاذب).
5. تحلیل خطا: طبقه‌بندی همهٔ شکست‌ها در taxonomy + سه داستان نماینده + Validitätsbedrohungen مشخص و صادقانه.

### پردهٔ ۴ — روایت و دفاع
1. مونتاژ نه نگارش: کارت‌های ۵ جمله‌ایِ هر فاز ← فصل‌های LaTeX؛ اگر حلقهٔ اجرا رعایت شده باشد، حدود ۸۰٪ متن از قبل وجود دارد.
2. code freeze: پس از آن فقط باگ‌فیکس.
3. Reproduction: fresh clone، فقط با دستورالعمل مکتوب، همهٔ اعداد دوباره تولید شوند.
4. Kolloquium: Präsentationskern + پاسخ اول کتبی و بعد شفاهی به پرسش‌نامه + جدول Antwortbarkeitsmatrix با اعداد واقعی + سه داستان خطا به‌عنوان قوی‌ترین اسلایدها.

## حلقهٔ اجرا و ریل‌ها

برای هر واحد کار (یک extractor، یک کوئری، یک آزمایش) سه گام:
- **Do** — کوچک‌ترین خروجی قابل‌تست با unit test.
- **Learn** — کارت ۵ جمله‌ای (مسئله/ورودی/روش/خروجی/محدودیت) + توضیح شفاهی ۹۰ ثانیه‌ای بدون نگاه به متن.
- **Present** — یک بلوک اسلایدی + یک ردیف AD log.

اگر گام سوم نشود، گام اول واقعاً تمام نشده — همین چک است که scope creep خاموش را متوقف می‌کند.

دو ریل نیز بعد از هر مرحله چک می‌شوند:
- **ریل scope:** هیچ آیتمی از لیست‌های شرطی/غیرالزام بی‌سروصدا core نشده؟ تخلف ← بازگشت به Future Work.
- **ریل evidence:** یک ادعا را تصادفی بردار؛ اگر در ۳۰ ثانیه منبعش را نشان ندهی، هنوز آمادهٔ پایان‌نامه نیست.

## ریل سوم: استراحت واقعی

دوره‌های نقاهت/تعطیلات به‌طور کامل از چرخهٔ کاری خارج‌اند. هیچ کار سبک، «فقط یک‌کم»، یا کار با ظرفیت پایین در این بازه‌ها برنامه‌ریزی نمی‌شود — نه حتی خواندن یادداشت‌ها یا پیش‌نویس نثر. اگر برنامه در نتیجهٔ این وقفه عقب بیفتد، مسئول جذب آن **بافر زمانی** است، نه ظرفیت کاهش‌یافتهٔ کاربر در دورهٔ استراحت. تصمیم دربارهٔ اینکه آیا این بازه اصلاً وارد نقشهٔ زمان‌بندی می‌شود یا نه، از قبل و صریح گرفته می‌شود؛ چیزی به‌صورت خزنده به آن اضافه نمی‌شود.

## تعریف «تمام»

پروژه وقتی تمام است که هر عدد پایان‌نامه از fresh clone بازتولید شود؛ روی هر سؤال نمونه، پاسخ + مسیر شواهد + وضعیت + دلیل موجود باشد؛ و بتوانی کل pipeline را در ۹۰ ثانیه توضیح دهی و به پرسش‌های متدولوژیک بدون نگاه جواب بدهی. هر چیز ناتمام، صادقانه در Future Work می‌نشیند — و این نشانهٔ بلوغ علمی است، نه ضعف.
